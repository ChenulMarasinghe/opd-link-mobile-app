# Static Code Review Findings

Read-only review of the current source. These are risks to verify, not executed defects; no code was changed.

| ID | File / function | Finding | Suggested follow-up | Severity |
|---|---|---|---|---|
| CR-01 | `src/services/adminService.ts` — `addDoctor`, `updateDoctor`, `deleteDoctor`, `addClinicWing`, `updateAppointmentStatus` | Some Firestore failures are caught while in-memory state is changed and presented as success. A user may believe a write persisted when it will disappear after restart. | Return persistence status, show offline/pending feedback and reconcile local state after reconnect. | High |
| CR-02 | `src/services/bookingService.ts` — `createAppointment` side effects after transaction | Appointment commits before queue max-token sync and notification creation; queue sync errors are caught. A booking can exist while the queue or confirmation notice is stale/missing. | Use a reliable retry/outbox path and expose partial side-effect status. | High |
| CR-03 | `src/services/verification.ts` — `sendVerificationCode` | Code generation uses `Math.random()` and writes a code before email delivery. EmailJS private key is referenced in client environment and can be extracted from a client app. | Generate/send codes in trusted backend; use secure randomness, rate limits and code cleanup. | High |
| CR-04 | `src/services/queueStatus.ts` — `notifyTurnApproaching`; `src/screens/patient/QueueStatusScreen.tsx` | Turn notification is triggered while the patient's queue screen evaluates state. This is not an independent background/push notification mechanism. | Use server-side queue triggers and push delivery; define duplicate/threshold behavior. | High |
| CR-05 | `src/services/backupService.ts` — `simulateBackup` | Manual action writes synthetic progress/size metadata and waits 1.5 seconds; it does not export or restore patient data. | Clearly label as simulation and implement/test real scheduled backup and restore separately. | High |
| CR-06 | `src/services/monitoringService.ts` — `getServiceStatus`, `getAuthenticationStatus`, `runMonitoringChecks` | Collection readability is treated as service health; auth check tests SDK app initialization, not authentication. Response time measures one `systemHealth` read. | Name checks to match their scope and add authenticated probes, intervals and alerting. | Medium |
| CR-07 | `src/services/queueStatus.ts` and `src/services/adminService.ts` — queue queries | Some paths use doctor/date/session while `queueDocId` uses doctor/date only. Session-specific and legacy queue records may be ambiguous. | Standardize queue identity around doctor + date + session and migrate old records. | High |
| CR-08 | `src/services/adminService.ts` — `advanceQueue`, `updateQueueStatus` | Queue advancement filters by appointment status/token while UI actions also change status/check-in. Cancellations, skipped tokens and concurrent callers need consistent reconciliation. | Define one transition model and transactionally test sparse tokens, cancellations, no-shows and concurrency. | High |
| CR-09 | `src/services/notificationService.ts` — `subscribeNotifications`, `createNotification` | Missing patient ID falls back to shared `patient_demo`; client code is not an authorization boundary. | Require explicit authenticated UID and enforce ownership in Firestore rules. | High |
| CR-10 | `src/services/bookingService.ts`; role routing in `src/app/index.tsx` | Client-side role routing does not prevent direct Firestore access. Security rules are not present in the reviewed client source. | Verify deployed rules prevent cross-patient access and limit admin/IT writes by role. | High |
| CR-11 | `src/services/adminService.ts` — `updateDoctor` | Doctor edits sync appointment name/department but not every snapshot field such as specialty/room; local and remote outcomes may differ. | Define historical appointment snapshot policy and test doctor edit behavior. | Medium |
| CR-12 | `src/services/maintenanceService.ts` — `getCurrentMaintenance`, `createMaintenance` | Current record selection uses schedule times without requiring `in-progress`; maintenance write and activity write can partially succeed. | Filter by intended status and use recoverable activity logging. | Medium |
| CR-13 | `src/services/backupService.ts`, `maintenanceService.ts`, `errorLogService.ts` | Backup/maintenance/error services provide read/create/update patterns but no delete operation. Delays provide create/read only. Avoid assuming full CRUD. | Document operation boundaries; add deletion only if approved product scope requires it. | Low |
| CR-14 | `src/services/adminService.ts` — `getAppointments`, `subscribeAppointments` | Queries order appointments by date; compound query variants elsewhere may require deployed Firestore indexes. | Run queries against the deployed test project and maintain index definitions if needed. | Medium |
| CR-15 | `src/services/verification.ts` — `verifyCode` | Expiry and attempt count are checked client-side. Concurrent guesses can race the attempts update and expired codes remain stored. | Enforce expiry/attempt limits atomically on a trusted backend and clean up code records. | Medium |
